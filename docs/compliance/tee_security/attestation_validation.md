# TEE Attestation Validation Procedures
## Security Compliance Documentation

### 1. Overview

This document outlines the attestation validation procedures implemented in the Aristo dual TEE architecture for NASDAQ market data processing. Our system uses both Intel SGX (Software Guard Extensions) and AMD SEV (Secure Encrypted Virtualization) technologies with a proprietary cross-attestation protocol to provide defense-in-depth security.

### 2. Intel SGX Attestation Process

#### 2.1 SGX Attestation Overview

Intel SGX attestation provides cryptographic proof that an enclave is running legitimate code with integrity on genuine Intel hardware. Our implementation uses the EPID (Enhanced Privacy ID) attestation scheme with the following workflow:

1. **Quote Generation**
   - SGX enclave computes a measurement (MRENCLAVE) of its initial state
   - Enclave generates a report containing MRENCLAVE, a nonce, and user data
   - Quoting Enclave signs the report using the platform's attestation key

2. **Quote Verification**
   - Quote is sent to Intel Attestation Service (IAS)
   - IAS verifies the signature against Intel's private EPID group key
   - IAS returns a signed attestation verification report

3. **Report Validation**
   - Our system validates the IAS signature on the verification report
   - The expected MRENCLAVE value is compared against the report
   - The report timestamp is verified for freshness

#### 2.2 SGX Attestation Implementation

```rust
fn verify_sgx_attestation(quote: &[u8], expected_mrenclave: &[u8; 32]) -> Result<(), AttestationError> {
    // Step 1: Send the quote to Intel Attestation Service
    let ias_report = ias_client.verify_quote(quote)?;
    
    // Step 2: Verify IAS signature on the verification report
    let ias_public_key = get_ias_public_key();
    if !crypto::verify_signature(&ias_report.signature, &ias_report.body, &ias_public_key) {
        return Err(AttestationError::InvalidSignature);
    }
    
    // Step 3: Parse the attestation verification report
    let report = parse_ias_report(&ias_report.body)?;
    
    // Step 4: Verify report status
    if report.status != "OK" {
        return Err(AttestationError::AttestationFailed(report.status));
    }
    
    // Step 5: Extract MRENCLAVE from the report
    let mrenclave = extract_mrenclave(&report)?;
    
    // Step 6: Compare with expected MRENCLAVE
    if mrenclave != expected_mrenclave {
        return Err(AttestationError::UnexpectedMeasurement);
    }
    
    // Step 7: Verify timestamp for freshness
    let report_time = parse_timestamp(&report.timestamp)?;
    let current_time = SystemTime::now();
    if current_time.duration_since(report_time)? > Duration::from_secs(86400) {
        return Err(AttestationError::AttestationTooOld);
    }
    
    Ok(())
}
```

#### 2.3 SGX Quote Structure

Our SGX quotes include the following fields to ensure complete verification:

| Field | Description | Validation Criteria |
|-------|-------------|---------------------|
| MRENCLAVE | Measurement of the enclave | Must match expected value for our WebAssembly runtime |
| MRSIGNER | Measurement of the signing entity | Must match our authorized development signing key |
| ATTRIBUTES | Enclave attributes | Must include INIT and DEBUG=0 flags |
| CONFIGSVN | Security Version Number | Must meet minimum SVN requirements |
| ISVSVN | ISV assigned SVN | Must meet minimum SVN requirements |

### 3. AMD SEV Attestation Process

#### 3.1 SEV Attestation Overview

AMD SEV provides VM memory encryption and secure attestation capabilities. Our implementation leverages SEV attestation to verify the integrity of the VM and its contents:

1. **Launch Measurement**
   - During VM launch, SEV firmware measures the initial VM state
   - This includes the kernel, initial ramdisk, and boot configuration
   - A launch measurement is generated by the AMD Secure Processor

2. **Attestation Report Generation**
   - VM requests an attestation report from the AMD-SP
   - Report includes the launch measurement and platform details
   - Report is signed with the platform's attestation key

3. **Report Verification**
   - The attestation report signature is verified using AMD's certificate chain
   - The measurement is compared against the expected value
   - Platform certificates are validated for authenticity

#### 3.2 SEV Attestation Implementation

```rust
fn verify_sev_attestation(report: &[u8], expected_measurement: &[u8; 32]) -> Result<(), AttestationError> {
    // Step 1: Parse the SEV attestation report
    let parsed_report = parse_sev_report(report)?;
    
    // Step 2: Verify the report signature using AMD certificate chain
    let amd_root_key = get_amd_root_key();
    let platform_cert = &parsed_report.platform_cert;
    
    if !crypto::verify_certificate_chain(platform_cert, &amd_root_key) {
        return Err(AttestationError::InvalidCertificateChain);
    }
    
    // Step 3: Verify report signature with platform key
    let platform_key = extract_platform_key(platform_cert)?;
    if !crypto::verify_signature(&parsed_report.signature, &parsed_report.body, &platform_key) {
        return Err(AttestationError::InvalidSignature);
    }
    
    // Step 4: Extract launch measurement
    let measurement = extract_measurement(&parsed_report)?;
    
    // Step 5: Compare with expected measurement
    if measurement != expected_measurement {
        return Err(AttestationError::UnexpectedMeasurement);
    }
    
    // Step 6: Verify report freshness
    let report_time = extract_timestamp(&parsed_report)?;
    let current_time = SystemTime::now();
    if current_time.duration_since(report_time)? > Duration::from_secs(3600) {
        return Err(AttestationError::AttestationTooOld);
    }
    
    Ok(())
}
```

#### 3.3 SEV Report Structure

Our SEV attestation reports include:

| Field | Description | Validation Criteria |
|-------|-------------|---------------------|

### 4. Cross-Attestation Protocol

#### 4.1 Cross-Attestation Overview

Our proprietary cross-attestation protocol provides defense-in-depth by requiring mutual verification between SGX and SEV environments:

1. **Initial Key Exchange**
   - SGX enclave generates a key pair and includes public key in its attestation report
   - SEV VM generates a key pair and includes public key in its attestation report
   - Both sides verify each other's attestation reports (as detailed above)
   - A shared secret is established using ECDH key exchange

2. **Ongoing Verification**
   - Regular re-attestation occurs at configurable intervals (default: 5 minutes)
   - Each re-attestation includes a new nonce to prevent replay attacks
   - Failure to complete re-attestation results in automatic isolation

3. **Cryptographic Evidence**
   - Each cross-attestation cycle generates a signed record
   - This record forms part of the regulatory audit trail
   - Records are stored in the RSA accumulator for efficient verification

#### 4.2 Cross-Attestation Implementation

```rust
fn perform_cross_attestation(sgx_node: &Node, sev_node: &Node) -> Result<AttestationProof, AttestationError> {
    // Step 1: Generate SGX attestation with embedded public key
    let sgx_keypair = crypto::generate_keypair()?;
    let sgx_attestation = sgx_node.generate_attestation(sgx_keypair.public_key())?;
    
    // Step 2: Generate SEV attestation with embedded public key
    let sev_keypair = crypto::generate_keypair()?;
    let sev_attestation = sev_node.generate_attestation(sev_keypair.public_key())?;
    
    // Step 3: Exchange and verify attestations
    sev_node.send_attestation(&sgx_attestation)?;
    sgx_node.send_attestation(&sev_attestation)?;
    
    let sev_verification = sgx_node.verify_peer_attestation()?;
    let sgx_verification = sev_node.verify_peer_attestation()?;
    
    if !sev_verification || !sgx_verification {
        return Err(AttestationError::CrossAttestationFailed);
    }
    
    // Step 4: Establish shared secret via ECDH
    let shared_secret = crypto::compute_ecdh(
        &sgx_keypair.private_key(), 
        &sev_attestation.public_key()
    )?;
    
    // Step 5: Create attestation proof
    let attestation_proof = AttestationProof {
        sgx_attestation: sgx_attestation,
        sev_attestation: sev_attestation,
        timestamp: SystemTime::now(),
        proof_id: generate_uuid(),
    };
    
    // Step 6: Sign the attestation proof with the shared secret
    let signed_proof = crypto::sign(&attestation_proof, &shared_secret)?;
    
    // Step 7: Add to RSA accumulator for efficient verification
    rsa_accumulator.add(&signed_proof)?;
    
    Ok(attestation_proof)
}
```

#### 4.3 Cross-Attestation Security Properties

The cross-attestation protocol provides the following security properties:

1. **Mutual Authentication**: Both TEE environments authenticate each other
2. **Defense in Depth**: System remains secure unless both TEE types are compromised
3. **Continuous Validation**: Regular re-attestation detects runtime compromise
4. **Non-Repudiation**: Cryptographic evidence of attestation for compliance
5. **Forward Secrecy**: New key material for each attestation cycle

### 5. WebAssembly Parameter Validation

#### 5.1 Dual-Format Parameter Validation

Our WebAssembly modules implement rigorous parameter validation to ensure memory safety:

1. **Length-Prefixed Format**
   - First 4 bytes represent a little-endian u32 length
   - Length is validated against reasonable bounds (0 < len <= 1024)
   - Buffer bounds are checked before any memory access

2. **Direct Format**
   - Used for fixed-size data without a length prefix
   - Expected size is specified in the validation context
   - Buffer bounds are checked against expected size

```rust
fn validate_parameters(buffer: &[u8], context: &ValidationContext) -> Result<ValidatedParams, ValidationError> {
    // Check if buffer is empty
    if buffer.is_empty() {
        return Err(ValidationError::EmptyBuffer);
    }
    
    // Try length-prefixed format first if enabled
    if context.support_length_prefix && buffer.len() >= 4 {
        let length = u32::from_le_bytes([buffer[0], buffer[1], buffer[2], buffer[3]]) as usize;
        
        // Check if length is reasonable
        if length > 0 && length <= context.max_param_size && buffer.len() >= length + 4 {
            let data = &buffer[4..4+length];
            return Ok(ValidatedParams::LengthPrefixed { length, data });
        }
    }
    
    // Try direct format if enabled and length-prefixed failed
    if context.support_direct_format && context.expected_direct_size > 0 {
        if buffer.len() >= context.expected_direct_size {
            let data = &buffer[0..context.expected_direct_size];
            return Ok(ValidatedParams::Direct { data });
        }
    }
    
    // Both formats failed
    Err(ValidationError::InvalidFormat)
}
```

#### 5.2 Memory Safety Implementation

To ensure memory safety within the WebAssembly environment:

1. **Bounds Checking**: All buffer accesses are bounds-checked
2. **Size Limiting**: Maximum parameter sizes are enforced
3. **Safe Copying**: Use of `core::cmp::min` to prevent buffer overflows
4. **Defensive Programming**: Always initialize default values

```rust
fn copy_validated_data(params: &ValidatedParams, dest: &mut [u8]) -> Result<usize, CopyError> {
    let source = match params {
        ValidatedParams::LengthPrefixed { data, .. } => data,
        ValidatedParams::Direct { data } => data,
    };
    
    // Safe copy using min to prevent overflow
    let copy_len = core::cmp::min(source.len(), dest.len());
    dest[0..copy_len].copy_from_slice(&source[0..copy_len]);
    
    Ok(copy_len)
}
```

### 6. Attestation Verification in Production

#### 6.1 Validator Network

Our production environment includes a validator network that verifies attestation proofs:

1. **Validator Responsibilities**
   - Verify SGX attestation reports against Intel IAS
   - Verify SEV attestation reports against AMD certificates
   - Validate cross-attestation proofs
   - Reach consensus on attestation validity

2. **Consensus Requirements**
   - 21-31 validators for market data only
   - 50-100+ validators when adding smart contracts
   - 2/3+ majority required for attestation acceptance

#### 6.2 Monitoring and Alerting

Attestation monitoring includes:

1. **Real-time Verification**
   - Continuous monitoring of attestation status
   - Immediate alerts for attestation failures
   - Automatic isolation of nodes failing attestation

2. **Attestation Metrics**
   - Success/failure rates by TEE type
   - Attestation latency tracking
   - Re-attestation frequency monitoring

3. **Compliance Reporting**
   - Automated generation of attestation summary reports
   - Cryptographic proof of continuous attestation
   - Audit-ready evidence of security controls

### 7. Side-Channel Protection

#### 7.1 Known Side-Channel Vectors

Our architecture implements protections against known TEE side-channel attacks:

1. **SGX Side-Channel Mitigations**
   - Spectre/Meltdown: Microcode updates and software mitigations
   - Page table attacks: Minimal page table interactions
   - Cache timing: Constant-time cryptographic operations
   - Power analysis: Limited exposure of sensitive operations

2. **SEV Side-Channel Mitigations**
   - VM boundary attacks: Latest AMD firmware with improved protections
   - Hypervisor snooping: SEV-SNP where available for enhanced protection
   - I/O attacks: Careful control of I/O operations

#### 7.2 Defense-in-Depth Protection

Our dual TEE approach provides inherent side-channel protection:

1. **Architectural Diversity**
   - Side-channels affecting SGX rarely impact SEV (and vice versa)
   - Exploitation would require different techniques for each TEE

2. **Cross-Validation**
   - Results from both TEE types must match
   - Side-channel compromise of one TEE would be detected

### 8. Attestation Recovery Procedures

#### 8.1 Attestation Failure Response

When attestation failures occur, the system follows these procedures:

1. **Immediate Isolation**
   - Failed node is immediately removed from the active mesh
   - Traffic is redirected to healthy nodes
   - Alert is triggered for security investigation

2. **Forensic Capture**
   - Memory dump (if possible) for offline analysis
   - Attestation report preservation
   - System logs capture

3. **Recovery Actions**
   - Node teardown and fresh deployment
   - Full re-attestation before returning to service
   - Root cause analysis to prevent recurrence

### 9. Conclusion

The attestation validation procedures detailed in this document form the security foundation of our dual TEE architecture. By combining Intel SGX and AMD SEV technologies with our proprietary cross-attestation protocol and WebAssembly parameter validation, we provide a defense-in-depth approach to securing NASDAQ market data processing.

This documentation serves as both a technical reference and a compliance artifact demonstrating the robustness of our security controls for regulatory review.
